# 단계 2: 방향성 있는 슬라이드 애니메이션

## 학습 목표
- 다음 달 = 오른쪽에서 들어오고 왼쪽으로 나감, 이전 달 = 그 반대.
- `.transition(.asymmetric(insertion:removal:))` 로 insertion/removal 방향 분리.
- `.id(value)` 트릭으로 view identity 를 강제 교체해 transition 트리거.

## 사전 산출물
- 단계 1 의 `prevMonth()` / `nextMonth()` + `rebuild(for:)`.
- `referenceDate`, `gridInterval`, `rows` 가 `@Published`.

## Swift / SwiftUI 개념

### `.transition(.asymmetric(insertion:removal:))`

15-3 의 `.transition(.opacity)` 는 insertion / removal 양쪽이 같은 효과였다. **비대칭 transition** 은:

```swift
.transition(.asymmetric(
    insertion: .move(edge: .trailing),  // 오른쪽 밖에서 들어옴
    removal:   .move(edge: .leading)    // 안에서 왼쪽 밖으로
))
```

이게 "다음 달" 슬라이드의 그림. "이전 달" 은 insertion/removal 의 edge 가 반대.

### `.id(value)` — view identity 강제 교체

15-3 의 ForEach 는 element 단위 identity 라 element 가 추가/제거될 때 transition 이 트리거됐다. **월 그리드는 ForEach 의 element 가 아니라 같은 view 가 내용만 바뀌는 구조** — SwiftUI 가 보기엔 "같은 view" 라 transition 이 안 트리거된다.

해결: `.id(referenceDate)` 부여. value 가 바뀌면 SwiftUI 가 "다른 view" 로 인식 → 기존 view removal + 새 view insertion → transition 발동.

```swift
GridView
    .id(store.referenceDate)
    .transition(slide)
```

> Vue 비유: `<Transition>` 안의 element 에 `:key="referenceDate"` 를 거는 결. key 가 바뀌면 vnode 가 새것으로 갈리면서 leave/enter 가 도는 그 패턴과 정확히 같다.

### 방향 state

asymmetric 의 edge 가 prev/next 에 따라 반대여야 함. store 에 방향 state 를 두고, prev/next 호출 시 **같은 트랜잭션 안에서** direction 과 referenceDate 를 같이 바꾸는 게 핵심:

```swift
enum SlideDirection { case forward, backward }

@Published private(set) var direction: SlideDirection = .forward

func prevMonth() {
    direction = .backward
    rebuild(for: prevDate)
}
func nextMonth() {
    direction = .forward
    rebuild(for: nextDate)
}
```

view 측에서 direction 에 따라 transition 분기:

```swift
private var slide: AnyTransition {
    switch store.direction {
    case .forward:
        .asymmetric(insertion: .move(edge: .trailing),
                    removal:   .move(edge: .leading))
    case .backward:
        .asymmetric(insertion: .move(edge: .leading),
                    removal:   .move(edge: .trailing))
    }
}
```

## 구현 가이드

### 1) 방향 state
- `CalendarStore` 에 `enum SlideDirection { case forward, backward }` 추가 (store 안에 nested 도 OK, top-level 도 OK).
- `@Published private(set) var direction: SlideDirection = .forward`.
- `prev/next` 가 호출되면 direction 을 **먼저** 세팅한 뒤 `rebuild(for:)`.

### 2) view 측 `.id` + `.transition` + `withAnimation`

월 그리드 (`VStack(spacing: 0) { ForEach(store.rows) { ... } }`) 에 세 modifier 부착:

```swift
VStack(spacing: 0) {
    ForEach(store.rows, id: \.first?.id) { row in
        WeekRowView(...)
    }
}
.id(store.referenceDate)
.transition(slide)
.clipped()            // ← 슬라이드 도중 옆으로 삐져나가는 view 잘라냄
```

버튼 액션을 `withAnimation` 으로 감싼다:

```swift
Button {
    withAnimation(.smooth(duration: 0.3)) {
        store.nextMonth()
    }
} label: { Image(systemName: "chevron.right") }
```

> view 쪽에 `withAnimation` 두면 store 가 깔끔. store 메서드 안에 두면 호출자가 까먹지 않음. 트레이드오프 학습 포인트 — 일단 view 쪽으로.

### 3) 기존 `.animation(_:value: allEvents)` 와의 공존

15-3 에서 그리드 `VStack` 에 `.animation(.smooth(duration: 0.25), value: allEvents)` 가 이미 붙어있음. 이건 이벤트 삭제용. 월 이동 트랜잭션과 충돌하진 않지만, 슬라이드 도중 이벤트 페이드도 같이 도는 게 부자연스러우면 그땐 위치/조건을 조정. 일단 그대로 두고 시각 확인.

## 함정 ①: 방향 전환 시 슬라이드가 어긋난다

위 1차 구현 (`prevMonth/nextMonth` 안에서 `direction` 과 `referenceDate` 를 한 번에 바꾸고, view 에서 `withAnimation` 으로 감쌈) 을 마치고 동작을 확인해 보면:

- **같은 방향 연속 클릭** (next → next → next 또는 prev → prev → prev) 은 자연스럽다.
- **방향을 바꾼 클릭** (next 후 prev, 또는 prev 후 next) 은 슬라이드가 "반대로 움직이는 느낌" 으로 어긋난다.

### 왜?

`.transition(slide)` 의 `slide` 는 `store.direction` 을 읽어 매번 계산되는 computed property. SwiftUI 는 transition 을 실제 발동시킬 때 두 view 의 modifier 를 **서로 다른 시점** 에서 가져온다:

- **들어오는 view (insertion)** → **현재 render** 의 modifier 값
- **나가는 view (removal)** → **마지막에 무대에 있던 시점 (= 직전 클릭 후)** 의 캐시된 modifier 값

`prevMonth()` 안에서 `direction = .backward` 와 `rebuild(...)` (= `referenceDate` 변경) 가 **같은 트랜잭션, 같은 render 패스에 batch** 된다. 떠나는 view 는 이번 render 에 더 이상 존재하지 않으니까 modifier 가 재평가되지 않고, **직전 render (= 이전 클릭 후) 의 direction 으로 removal 방향이 박혀버린다**.

### 시나리오 (Oct → Nov → Oct)

| 단계 | direction (state) | 떠나는 view 의 캐시 | 들어오는 view 의 새 값 | 결과 |
|---|---|---|---|---|
| ① 초기 | `.forward` | — | — | — |
| ② next 클릭 | `.forward` | (Oct) `.forward` → removal `.leading` | (Nov) `.forward` → insertion `.trailing` | ✅ 자연스러움 |
| ③ prev 클릭 | `.backward` | (Nov) **`.forward`** ← 캐시 → removal `.leading` | (Oct) `.backward` → insertion `.leading` | ❌ 둘 다 왼쪽 |

③ 단계에서 떠나는 Nov 의 removal 은 `.leading` (왼쪽으로), 들어오는 Oct 의 insertion 은 `.leading` (왼쪽에서). 둘이 같은 쪽에서 엇갈리는 꼴 → 사용자 눈엔 "반대로 움직이는 느낌". 같은 방향 연속 클릭은 캐시와 새 direction 이 일치해서 문제가 안 보임.

### 수정 — 두 render 패스로 쪼개기

같은 트랜잭션에서 둘 다 바꾸지 말고, `direction` 변경과 `rebuild` 호출 사이에 **render 한 번이 끼이게** 만든다:

```
1단계 (즉시):     direction = .backward
                 → SwiftUI 가 한 번 다시 그림 (애니메이션 X)
                 → 떠날 view 의 transition modifier 캐시가 새 direction 으로 갱신됨

2단계 (다음 tick): withAnimation { rebuild(...) }
                 → 이제서야 떠남, 갱신된 캐시대로 올바른 방향으로
```

쪼개는 도구는 `DispatchQueue.main.async { ... }` — "지금 말고 다음 runloop tick 에 실행" 이라는 뜻. JS 의 `setTimeout(fn, 0)` 으로 batching 을 강제로 떼어내는 그 패턴과 동일.

### 어디에 둘 것인가 — store vs view

**A. store 안에서 쪼개기** ← 선택

```swift
// CalendarStore.swift
import SwiftUI  // withAnimation 때문

func prevMonth() {
    direction = .backward
    DispatchQueue.main.async { [weak self] in
        guard let self else { return }
        withAnimation(.smooth(duration: 0.3)) {
            let prev = Calendar.current.date(byAdding: .month, value: -1, to: self.referenceDate) ?? self.referenceDate
            self.rebuild(for: prev)
        }
    }
}
```

호출자는 한 줄로 단순화:

```swift
HoverButton { store.prevMonth() } label: { ... }   // withAnimation 제거
```

**B. view 안에서 쪼개기** (선택지 비교용)

```swift
HoverButton {
    store.setDirection(.backward)        // direction 만 세팅하는 메서드 노출
    DispatchQueue.main.async {
        withAnimation(.smooth(duration: 0.3)) {
            store.prevMonth()             // refDate 만 변경
        }
    }
}
```

**왜 A 인가**

- prev/next 두 호출 지점이 매번 트릭을 반복해야 하는 B 와 달리, A 는 store 내부에만 트릭이 있어 호출 지점이 늘어도 안전 (키보드 단축키·swipe 제스처 추가 시 자동 적용).
- 16-1 의 "**rebuild 단일 진입점**" 정신과 일치 — "store 메서드 하나 = 완성된 한 동작".
- "direction 과 referenceDate 가 두 단계로 갱신돼야 한다" 는 batching 회피 룰은 모델 레이어 책임으로 보는 게 자연스러움.
- 단점: store 가 `import SwiftUI` 를 가지게 됨. 다만 이미 `ObservableObject` (Combine) 로 SwiftUI 와 한 쌍이라 큰 위반 X.

Spring 비유: A 는 Service 에 `@Transactional` 을 박아 호출자가 트랜잭션을 신경 안 쓰게 하는 패턴 / B 는 Controller 가 트랜잭션 시작·커밋을 매번 직접 챙기는 패턴.

## 함정 ②: clip 박스가 transition 과 함께 끌려간다

①의 방향 전환 함정을 고친 뒤에도, **사이드바를 펼친 상태**에서 월을 바꾸면 leaving 그리드가 **사이드바 영역 위까지 비집고 들어와 보이는** 또 다른 증상이 남는다. 1차 구현에서 그리드 VStack 의 modifier 체인 끝에 붙여둔 `.clipped()` 가 사실 제대로 동작하지 않고 있던 것.

### 왜?

`.clipped()` 가 `.transition(slide)` 와 **같은 modifier 체인** 안에 매달려 있으면, SwiftUI 가 transition 으로 view 를 offset 시킬 때 **clip 박스도 view 와 함께 끌려간다**. leaving 그리드가 화면 밖으로 밀려나는 동안 자기 clip 영역도 같이 이동 → 사실상 clip 이 동작을 안 함.

```
VStack { ForEach...rows }
    .id(referenceDate)
    .transition(slide)
    .clipped()         ← transition 체인의 끝.
                         transition 의 offset 이 걸리면
                         이 clip 박스도 같이 끌려감.
```

ContentView 의 레이아웃을 보면:

```
ZStack {
    HStack {
        Sidebar.frame(width: 240 or 0).clipped()
        ZStack { Color.clear, MonthlyCalendarView, FloatingToolbar }   ← 오른쪽 pane
    }
}
```

leaving 그리드가 오른쪽 pane 의 좌측 경계 (= 사이드바 우측 끝) 를 넘어가도 안 잘리니까 사이드바 위로 보임.

### 수정 — clip 을 stable 한 outer view 로 옮긴다

`.clipped()` 를 **transition 의 영향을 받지 않는 상위 view** 에 적용. 가장 간단한 방법은 MonthlyCalendarView 의 outermost VStack:

```swift
var body: some View {
    VStack(spacing: 0) {
        // 헤더 / 요일 / 그리드
        ...
        VStack(spacing: 0) {
            ForEach(store.rows, ...) { ... }
        }
        .id(store.referenceDate)
        .animation(.smooth(duration: 0.25), value: allEvents)
        .transition(slide)
        // .clipped() 는 여기서 제거
    }
    .padding(.top, 35)
    .clipped()    // ← outermost VStack 에 적용
}
```

이 outer VStack 은 `.id` 가 없으니 refDate 변경에 영향 X → **stable 한 부모**. 그 frame 은 MonthlyCalendarView 의 자연 크기 (= 오른쪽 pane 너비 × 높이). 안쪽에서 grid VStack 이 transition 으로 좌우 offset 돼도 이 outer frame 에 잘린다.

### 학습 포인트

- `.clipped()` 는 **자기가 적용된 view 의 frame** 을 기준으로 clip 한다.
- `.transition(.move(edge:))` 의 offset 은 **자기가 적용된 view (와 그 children)** 를 이동시킨다.
- 둘이 같은 modifier 체인에 있으면, transition 의 offset 이 `.clipped()` 의 **frame 자체** 를 이동시키는 효과 → clip 이 무의미해진다.
- 해결: clip 을 transition 보다 **명백히 바깥쪽** 의 stable parent 에 둔다.

> Vue/CSS 비유: `<Transition>` 의 element 자체에 `overflow: hidden` 을 주면, 그 element 가 `translateX` 될 때 overflow box 도 같이 움직임. 잘리길 원하면 부모에 줘야 한다 — 정확히 같은 결.
