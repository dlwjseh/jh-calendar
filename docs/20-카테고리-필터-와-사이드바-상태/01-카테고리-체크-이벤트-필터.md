# 단계 1: 카테고리 체크 → 이벤트 표시/숨김 필터

## 학습 목표
- 사이드바 카테고리 체크박스를 끄면 그 카테고리의 이벤트가 달력/팝업에서 **즉시 사라지고**, 켜면 다시 나타나게 한다.
- "다른 모델(Category)의 값으로 이벤트를 거르는" 관계 순회 필터를, 토글 시 **실시간 반영**되도록 올바른 위치에 둔다.

## 사전 지식
- `Category.isChecked: Bool` 이 이미 있고 `CategoryRow` 의 체크박스가 토글한다 (`JHCalendar/Features/Sidebar/CategoryRow.swift:12`).
- `Event.category: Category?` 로 이벤트가 카테고리를 가리킨다 (`EventModels.swift:8`).
- 이벤트를 그리는 두 지점:
  - `MonthlyCalendarView` — `@Query allEvents` → `events`(멀티데이용) / `singleDayEventsByDayIndex`(단일-일용)
  - `DayPopupDialog` — `@Query dayEvents` → `visibleEvents`
- 19-04 에서 배운 "DB(`#Predicate`)로 못 거르는 건 메모리에서 거른다" 패턴.

## Swift / SwiftUI 개념

### 1) 관계 순회 필터링
거르는 기준이 `Event` 자신이 아니라 **연결된 `Category`** 에 있다. Swift 옵셔널 체이닝으로 타고 들어가 본다.

```swift
event.category?.isChecked ?? true
//          └ Category? 옵셔널 체이닝   └ category 가 nil(미지정)이면?
```

- `category` 가 `nil`(카테고리 없는 이벤트)일 때의 정책을 `??` 로 정한다. **기본: `true`(항상 표시)** — 비범위 참고. JS 의 `event.category?.isChecked ?? true` 와 사실상 동일한 표현이다.

### 2) 왜 `#Predicate`(DB) 가 아니라 인메모리인가 — 그리고 반응성
이게 이 단계의 핵심이자 함정이다.

- `@Query` 는 **그 쿼리 대상 타입의 변화**를 관찰한다. `allEvents` 는 `Event` 를 관찰하지 `Category` 를 관찰하지 않는다. 그래서 `isChecked`(Category 의 값)를 **`#Predicate` 안에서** 걸면, 체크박스를 토글해도 *Event 는 안 바뀌었으니* 쿼리가 다시 안 돌아 화면이 그대로일 수 있다.
- 해결: 거르기를 **뷰의 computed property(= body 평가 중 실행되는 코드)** 에서 한다. SwiftData `@Model` 은 `@Observable` 이라, **body 안에서 `category.isChecked` 를 읽으면** SwiftUI 가 그 Category 를 의존성으로 추적한다 → 토글하면 자동 재렌더.

> Spring/JS 비유로, "쿼리 한 방으로 다 거르려" 하기보다 후보를 가져온 뒤 화면 그리는 쪽에서 거르는 것. 19-04 의 반복 매칭과 똑같은 구조다. → [19-04](../19-이벤트-반복/04-반복-펼치기-엔진.md)

핵심 규칙: **필터를 `body`/computed 안에 두고, 거기서 `isChecked` 를 읽어라.** init 의 `#Predicate` 로 옮기지 말 것.

## 구현 가이드
> 정답 풀코드는 제공하지 않는다. 직접 작성.

### A) 달력 — `MonthlyCalendarView`
지금 이벤트 소스가 두 군데서 `allEvents` 로 시작한다:
- `events`(11~16번 줄) — 멀티데이 경로
- `singleDayEventsByDayIndex`(17~28번 줄) — 단일-일 경로

두 곳 **모두** 카테고리 체크 필터를 통과시켜야 한 카테고리를 꺼도 단일/멀티데이가 같이 사라진다.

힌트:
- 매번 `.filter { $0.category?.isChecked ?? true }` 를 두 곳에 적기보다, **체크된 것만 담은 base computed** 하나(`shownEvents` 같은)를 만들고 두 경로가 그걸 쓰게 하면 중복이 준다.
- 단, base 를 만들든 아니든 그 필터는 **computed 안**에 있어야 반응성이 산다(위 개념 2).

```swift
private var shownEvents: [Event] {
    allEvents.filter { /* TODO: 카테고리 체크 통과 */ }
}
// events, singleDayEventsByDayIndex 의 출발점을 allEvents → shownEvents 로
```

### B) 일 팝업 — `DayPopupDialog`
이미 `visibleEvents`(37~48번 줄)에서 인메모리 필터를 하고 있다. 거기에 카테고리 조건을 **AND** 로 더하면 된다.

힌트:
- 기존 `.filter { ... }` 클로저 안에서, 반복/겹침 판정을 통과하더라도 **카테고리가 꺼져 있으면 제외**.
- `return (기존 판정) && (event.category?.isChecked ?? true)` 형태.

## 자가 점검 (구현 후)
- 빌드 통과? (⌘B)
- 체크박스를 끄면 그 카테고리 이벤트가 **즉시** 달력에서 사라지나? 켜면 다시?
- 멀티데이 이벤트도 같이 사라지나? 일 팝업에서도?
- 카테고리 없는 이벤트는 그대로 보이나?
- 반복 이벤트도 그 카테고리를 끄면 다 같이 사라지나?
- 퀴즈: 왜 `isChecked` 필터를 `#Predicate`(init) 가 아니라 computed 에 두는가? — `@Query allEvents` 는 Category 변화를 관찰하지 않아 토글이 반영 안 될 수 있음. body 에서 읽어야 `@Observable` 의존성이 걸림.
