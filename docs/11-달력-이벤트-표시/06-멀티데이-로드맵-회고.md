# 단계 6: 멀티 데이 로드맵 & 회고 (문서 전용 · 코드 없음)

> 이 단계는 **구현이 없다.** 이번 기능을 단일 일로 마무리하면서, 멀티 데이 일정을 어떻게 올릴지 설계 의도를 기록으로 남긴다. (memory: 멀티데이까지 생각한 설계를 문서로.)

## 지금까지의 설계가 멀티데이를 위해 미리 해둔 것

| 결정 | 단일 일에서 한 일 | 멀티데이가 그대로 쓰는 이유 |
|---|---|---|
| `Event.endDate` 저장 (01) | 보통 start 와 같은 날 | 기간의 끝을 이미 알고 있음 → 모델 변경 불필요 |
| `eventsByDay(_:)` 순수 함수 (03) | `startOfDay(startDate)` 한 키에만 append | 멀티데이는 **이 함수 내부만** start~end 루프로 교체 |
| 멍청한 셀 `DayCellView(events:)` (04) | 받은 것만 그림 | 어느 날에 속하는지 판단을 셀이 안 함 → 변경 불필요 |
| `+N` 오버플로우 (05) | 셀당 렌더 상한 | 멀티데이로 행이 늘어도 비용 상한 유지 |

→ **데이터/조회 측면은 이미 멀티데이 ready.** 남은 건 *렌더링* 뿐.

## 멀티데이가 진짜로 어려운 지점: 렌더링

단일 일은 "각 칸 안에 독립 바" 면 됐다. 멀티데이 종일 일정은 **여러 칸을 가로지르는 하나의 연속 바**여야 자연스럽다. 그런데 현재 구조는 `HStack { ForEach(row) { DayCellView } }` — **셀이 자기 칸을 못 벗어난다.** 칸 안에서 각자 바를 그리면 연속이 아니라 토막난 바가 된다.

그래서 필요한 후속 작업(다음 기능 후보):

1. **주(week) 행 단위 레이아웃으로 승격**
   - 바 그리기를 셀이 아니라 **주 행(row) 컨테이너**가 담당.
   - 그 주에 걸친 멀티데이 이벤트를, 시작 칸~끝 칸을 덮는 가로 바로 `overlay`/좌표 계산해 그림. (셀 너비 = 행너비/7 로 위치·길이 산출.)
   - 주 경계를 넘으면 각 주마다 토막내서 그림 (캘린더 표준 동작).

2. **lane(트랙) 배치 — 겹침 처리**
   - 같은 주에 멀티데이가 여러 개 겹치면 세로로 단(lane)을 나눠 쌓아야 함.
   - 인터벌 그래프 색칠 류의 단순 그리디: 시작순 정렬 → 빈 lane 에 배치. 03 인덱스를 입력으로 쓰는 **또 다른 순수 함수**(`assignLanes(...)`)로 분리하면 셀/행 렌더와 독립 테스트 가능.

3. **단일 일과의 공존**
   - 단일 일 바/동그라미는 지금 셀 내부 방식 유지, 멀티데이 연속 바만 행 오버레이로. 한 셀 안에서 두 레이어의 세로 위치(겹침)를 어떻게 합칠지 결정 필요.

> 위 1~3은 **이번 기능 범위 밖**. 새 기능 번호로 따로 진행한다. 여기서는 "왜 지금 구조가 그쪽으로 무리 없이 확장되는가" 만 확정해 둔 것.
