# 단계 2: 표시 범위 이벤트 조회 (@Query + Predicate + 정렬)

## 학습 목표
`MonthlyCalendarView` 에서 **현재 화면에 보이는 날짜 범위에 걸친 이벤트만** `@Query` 로 가져오고 `startDate` 순으로 정렬한다.

## 사전 지식
- `@Query` 기본 사용 → `ContentView.swift:5` (`@Query private var folders: [Folder]`) 참고. 여기서는 **기본 @Query 는 재설명하지 않는다.**
- `MonthlyCalendarView` 는 `@StateObject store = CalendarStore()`, `store.rows: [[DayCell]]`, `store.referenceDate` 보유
- 그리드 날짜 범위 계산 로직은 `CalendarMath.makeDayCells(for:)` 안에 있음 (gridStart ~ total일)

## Swift / SwiftUI 개념
이 단계의 **새 측면**: `@Query` 에 **`#Predicate` 필터 + 정렬**을 주는 것. (`@Query` 자체는 이미 다룸 → 위 링크.)

- `#Predicate<Event> { $0.startDate >= start && $0.startDate < end }`
  - **DB 의 `WHERE` 절**과 같다. Spring Data JPA 의 `findByStartDateBetween(...)`, JS 라면 `events.filter(e => ...)` 에 대응. 차이: 필터가 **저장소 단에서** 적용돼 안 보이는 데이터까지 메모리로 끌어오지 않는다.
- 정렬: `@Query(sort: \Event.startDate)` 또는 `SortDescriptor`. → `ORDER BY startDate`.
- **동적 predicate** (월이 바뀌면 범위도 바뀜): `@Query` 는 프로퍼티 래퍼라 선언 시점에 값이 고정된다. 범위를 동적으로 주려면 **커스텀 `init` 에서 `_events = Query(filter:sort:)` 로 초기화**한다.

```swift
struct MonthlyCalendarView: View {
    @Query private var events: [Event]

    init(/* 필요시 referenceDate */) {
        // TODO: gridStart, gridEnd 계산
        let predicate = #Predicate<Event> { e in
            e.startDate >= gridStart && e.startDate < gridEnd
        }
        _events = Query(filter: predicate, sort: \Event.startDate)
    }
}
```

> ⚠️ `#Predicate` 안에서는 쓸 수 있는 표현이 제한적이다(복잡한 함수 호출 X). `Calendar` 호출은 predicate **밖에서** 미리 계산한 `Date` 상수만 비교에 쓴다.

## 구현 가이드
- 그리드 범위 = 첫 셀 날짜 ~ 마지막 셀 다음 날. `CalendarMath` 의 계산을 재사용하거나, `store.rows.first?.first?.date` ~ `store.rows.last?.last?.date` + 1일 로 잡는 방법도 있다. (단, `@Query` init 은 `store` 초기화 전이라 타이밍 주의 → 범위 계산을 `CalendarMath` 의 **순수 함수**로 빼서 init 에서 직접 호출하는 쪽이 깔끔.)
- **현 단계 범위 한정**: 월 이동 UI 가 아직 없다. 지금은 `referenceDate` 가 고정이므로, 정 어려우면 1차로 `@Query(sort: \Event.startDate) var events`(전체 조회)로 두고 범위 predicate 는 TODO 주석으로 남겨도 된다. 단, **권장은 predicate 적용** — 이유는 아래.

### 성능/설계 노트 (솔직하게)
- 개인 캘린더 한 달 이벤트는 보통 수십~수백 개다. 이 규모에선 전체 조회 후 메모리에서 걸러도 체감 차이는 사실상 없다 (조기 최적화 주의 — memory: 성능 우려 = 조기 최적화).
- 그럼에도 predicate 를 권장하는 진짜 이유는 **속도보다 정합성·확장성**: 월 이동/멀티데이가 들어오면 "보이는 범위만" 이라는 경계가 명확해야 03 의 인덱스가 단순해진다. 그러니 "성능 때문에" 보다 "범위를 모델 단에서 명시" 한다고 이해할 것.
